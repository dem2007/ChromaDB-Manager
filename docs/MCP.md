# MCP-сервер ChromaDB Manager

Справочник по инструментам, параметрам и ответам. Всё, что здесь написано,
взято из исходников (`Sources/ChromaCore/MCP/`) и проверено на живом сервере.

---

## 1. Как это устроено

```
агент  ──stdio──►  chromadb-mcp  ──сокет Unix──►  приложение  ──HTTP──►  ChromaDB
```

**`chromadb-mcp`** — вспомогательный исполняемый файл внутри бандла:

```
ChromaDB Manager.app/Contents/MacOS/chromadb-mcp
```

Своей логики у него нет: ни инструментов, ни прав, ни доступа к базе. Он
переносит сообщения по сокету `~/Library/Application Support/ChromaDBManager/mcp.sock`.
Решение «что агенту можно» принимается в одном месте — в приложении.

**Приложение должно быть запущено.** Без него сокета нет, и помощник ответит
отказом.

**Формат сообщений** — JSON-RPC 2.0, по одному сообщению на строку (разделитель
`\n`). В `stdout` уходят только сообщения протокола; всё прочее — в `stderr`.

### Версии протокола

| | значение |
|---|---|
| основная | `2026-07-28` |
| поддерживаются также | `2025-06-18`, `2025-03-26`, `2024-11-05` |

### Методы

| метод | назначение |
|---|---|
| `initialize` | рукопожатие старой эпохи |
| `notifications/initialized` | уведомление, ответа не требует |
| `server/discover` | рукопожатие новой эпохи |
| `tools/list` | список инструментов |
| `tools/call` | вызов инструмента |
| `ping` | проверка живости, пустой результат |
| `notifications/cancelled` | отмена начатого вызова |

### Схема ответа

Инструмент, объявивший `outputSchema`, **обязан** возвращать `structuredContent`
по ней. Это не пожелание: клиент сверяет ответ со схемой сам и при расхождении
выбрасывает ответ целиком, отдавая агенту ошибку валидации вместо данных.

Живой случай: `get_file` с `outline` отдаёт `sections` и не отдаёт `documents`,
а схема требовала `documents`. Карта файла на 1281 чанк не дошла до агента ни
разу — он читал числа из текста ошибки и дальше угадывал названия разделов.

Поэтому у инструмента с несколькими видами ответа схема описывает **все** и
требует только то, что есть в каждом. Согласие ответа со своей схемой проверяется
на каждой ветке каждого инструмента — включая пустую выдачу и промах по имени.

## 2. Подключение

Ключ клиента заводится в приложении на экране «Клиенты» и показывается **один
раз** — хранится он только хешем.

### Файл конфигурации

`~/Library/Application Support/Claude/claude_desktop_config.json`

```json
{
  "mcpServers": {
    "chromadb-manager": {
      "command": "/Applications/ChromaDB Manager.app/Contents/MacOS/chromadb-mcp",
      "env": {
        "CHROMADB_MCP_KEY": "ключ-клиента"
      }
    }
  }
}
```

### Одной командой

```bash
hermes mcp add chromadb-manager --command "/Applications/ChromaDB Manager.app/Contents/MacOS/chromadb-mcp" --env CHROMADB_MCP_KEY=ключ-клиента
```

Команда от Hermes, а не от Claude Code: `claude` на машине может не стоять
вовсе. Ключи взяты у живого `hermes mcp add --help`. Для агента без своего
CLI годится JSON выше — файл у каждого свой:

| агент | файл |
|---|---|
| Hermes | `~/.hermes/config.yaml` (дерево `mcp_servers`) |
| Bionic | `~/.lmstudio/mcp.json` (объект `mcpServers`) |
| Claude Desktop | `~/Library/Application Support/Claude/claude_desktop_config.json` |

### Кнопкой из приложения

На карточке клиента, в разделе «Подключение агента», два ряда кнопок — по
одной на каждого агента, найденного на этой машине:

- **«Прописать сервер в агента»** — вписывает настройку **вместе с ключом**,
  так что после перезапуска агента всё работает. Кнопка ждёт ключ: он есть
  на руках только сразу после выпуска, потому что приложение хранит его
  хешем (7.4). Перевыпустите ключ — и кнопка запишет настройку с ним.
- **«Положить агенту SKILL.md»** — кладёт скилл туда, где агент его читает.

Обе кнопки **спрашивают перед записью**: правится чужой файл, который человек
ведёт руками, и ответ называет, какой именно и что прежний сохранится снимком.

| агент | конфигурация | скилл |
|---|---|---|
| Hermes | `~/.hermes/config.yaml`, дерево `mcp_servers` | `~/.hermes/skills/research/chromadb-manager/SKILL.md` |
| Bionic | `~/.lmstudio/mcp.json`, объект `mcpServers` | `~/.lmstudio/skills/chromadb-manager/SKILL.md` |

Пути и форматы взяты с живых установок, а не из документации: у Bionic
расположение скиллов описано его же встроенным `skill-management`, и имя
папки обязано совпадать с `name` из шапки.

**Чужое не трогается.** Конфигурация Hermes — документ, который человек ведёт
руками: там его модели, ключи других сервисов и сотни строк комментариев.
Меняется ровно один блок `chromadb-manager`, остальное остаётся как было,
а прежний файл кладётся рядом снимком `config.yaml.bak-…`. У Bionic то же
самое через разбор JSON: чужие серверы и поля сохраняются. Файл, который не
удалось разобрать, **не перезаписывается** — ответ говорит об этом прямо.

Кнопка ставит **английский** скилл — на этом языке отвечает и сам сервер.
Русский вариант, `SKILL.ru.md`, лежит рядом в приложении и копируется
вручную: `ChromaDB Manager.app/Contents/Resources/Skills/chromadb-manager/`.
Оттуда же берут файл те, кому кнопка не подошла: другой агент, другая
машина, свой каталог скиллов.

**Чего кнопка не делает.** Если строка `mcp_servers:` — не обычное дерево,
а запись серверов в строку, якорь или ссылка, она отказывается и **не трогает
файл**: разобрать такое нечем, а переписать строку значит удалить чужое.
Пустую запись (`{}`, `null`, `~`) она разворачивает в дерево вместе с
комментарием при ней: терять там нечего, кроме заметки человека.

**Права файлов.** Снимок получает те же права, что и оригинал, а
конфигурация, которой ещё не было, создаётся с `0600`. Не мелочь: замерено,
что перезапись существующего файла права сохраняет, а **новый** получает
`0644` по umask — и снимок `config.yaml`, где лежат ключи человека к другим
сервисам, оказался бы доступен на чтение всем в системе. Свои снимки Hermes
держит в `0600`.

**Скилл обновляется на своём месте.** Скиллы Hermes разложены по разделам,
и агент опознаёт скилл по имени в шапке: если `chromadb-manager` уже лежит
в каком-то разделе, кнопка обновит его там, а не положит вторую копию
в `research` — иначе у агента вышло бы два скилла с одним именем.

### Проверка из терминала

```bash
CHROMADB_MCP_KEY=ключ-клиента "/Applications/ChromaDB Manager.app/Contents/MacOS/chromadb-mcp" <<'EOF'
{"jsonrpc":"2.0","id":1,"method":"tools/list"}
EOF
```

## 3. Права и потолки

Права принадлежат **ключу**, а не серверу. Инструменты, недоступные ключу, не
показываются в `tools/list` вовсе — но проверка при вызове всё равно остаётся.

| право | что открывает |
|---|---|
| чтение | `list_collections`, `describe_collection`, `search`, `get_documents`, `get_file`, `collect_mentions`, `list_files` |
| запись | `add_documents` |
| удаление | `delete_documents` — **отдельное** право, право записи его не даёт |

| потолок | умолчание | что ограничивает |
|---|---|---|
| результатов в вызове | 10 | `n_results`, `limit`; у `collect_mentions` считает файлы |
| результатов без указания | 5 | когда параметр не передан |
| знаков в одном документе | 4000 | длинный текст обрезается с пометкой |
| знаков в ответе целиком | 24 000 | ответ обрезается с пометкой |
| коллекций в одном поиске | 5 | `collections` |

Запрос сверх потолка **не отвергается**: выдача урезается, и об этом сказано в
ответе текстом.

Отдельно действуют ограничения частоты: запросов в минуту, всплеск, записей в
минуту, документов в сутки, размер одного документа.

### Чего через MCP нельзя

- создать или удалить коллекцию;
- передать готовый эмбеддинг — вектор считает приложение;
- получить векторы из базы;
- удалить документы по фильтру — только по явному списку идентификаторов;
- перезаписать существующий документ.

## 4. Общие параметры

### `filter` — условие по метаданным

Синтаксис ChromaDB. Поддерживаются `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`,
`$in`, `$nin`, а также `$and` и `$or` со списком условий.

```json
{"filter": {"$and": [{"year": {"$eq": 2026}}, {"doc_type": {"$in": ["Документ", "Заключение"]}}]}}
```

Имена и типы полей — из `describe_collection`. Сравнение с числом `2026` и со
строкой `"2026"` — разные условия, второе вернёт пустую выдачу.

**Поиска подстроки здесь нет.** `$regex` и `$like` база отклоняет с невнятным
«Invalid where clause», а `$contains` и `$not_contains` — принимает и не находит
по ним ничего: замерено на chroma 1.4.4, где `{"doc_type": {"$contains": "ПР10"}}`
дал ноль записей при 1699 подходящих. Оба случая приложение отклоняет само,
называя оператор и говоря, чем его заменить: подстрока в тексте — параметр
`contains`, раздел документа — `heading` у `get_file`.

### `file_types` — тип исходного файла

Человеческое слово вместо перечисления расширений.

| значение | расширения |
|---|---|
| `word` | `.docx`, `.doc`, `.odt`, `.rtf`, `.pages` |
| `excel` | `.xlsx`, `.xls`, `.xlsm`, `.ods`, `.numbers`, `.csv`, `.tsv` |
| `pdf` | `.pdf` |
| `presentation` | `.key`, `.pptx` |
| `text` | `.txt`, `.md`, `.markdown` |
| `web` | `.html`, `.htm` |
| `book` | `.epub` |
| `code` | `.swift`, `.py`, `.js`, `.ts`, `.sh`, `.sql` |
| `data` | `.json`, `.xml`, `.yaml`, `.yml` |

Список — то, что сборка **умеет читать**: `presentation` означает `.pptx`
и `.key`, потому что `.ppt` и `.odp` эта сборка не извлекает.

Принимается и само расширение: `"docx"`. Несколько значений складываются по
«или», с `filter` — по «и».

```json
{"file_types": ["excel", "pdf"]}
```

### `contains` — подстрока в тексте документа

Регистр учитывать не нужно: спрашиваются обычные варианты написания — как
передано, строчными, С Заглавной, а для коротких слов и ПРОПИСНЫМИ. «astra»
найдёт «Astra». Написание «AsTrA» так не найдётся: база сравнивает подстроки
буквально.

### `fields` — какие поля метаданных вернуть

Список имён. Не задан — возвращаются все поля, как и раньше.

```json
{"fields": ["source_file", "стоимость_тыс_руб"]}
```

**На отбор документов не влияет.** Фильтр по-прежнему работает по всем полям —
меняется только то, что попадёт в ответ. Предупреждения (плоская таблица,
неполная книга) и отпечаток файла читаются из полных метаданных и никуда
не деваются.

Зачем: строка таблицы тащит в ответ **все свои колонки**, а бюджет ответа
считает метаданные наравне с текстом. Замер на живой коллекции (1290 строк
таблиц):

| выборка | метаданных на строку | строк в ответе на 24 000 |
|---|---|---|
| сто самых широких строк | 1883 → **94** | 8 → **56** |
| сто строк вразброс | 419 → **87** | 49 → **100** |

Имя, которого нет ни у одного документа в выдаче, называется в ответе: опечатка
в названии колонки иначе выглядит как «в базе про это пусто».

## 5. Инструменты

### 5.1. `list_collections` — список коллекций

Право: **чтение**. Параметров нет.

Возвращает только коллекции, открытые ключу. Отсутствие коллекции в списке не
значит, что её нет в базе.

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"list_collections","arguments":{}}}
```

Ответ — `collections[]`: имя, число документов, модель эмбеддинга, метрика.

---

### 5.2. `describe_collection` — устройство коллекции

Право: **чтение**.

| параметр | тип | обяз. | описание |
|---|---|---|---|
| `collection` | строка | да | имя из `list_collections` |

Отдаёт поля метаданных: имя, тип, обязательность, встречающиеся значения. Если
схемы у коллекции нет, поля перечисляются по тому, что реально записано.

```json
{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"describe_collection","arguments":{"collection":"base_docs"}}}
```

Вызывать **до** построения фильтра: без этого фильтр строится наугад.

---

### 5.3. `search` — поиск по смыслу

Право: **чтение**.

| параметр | тип | обяз. | умолчание | описание |
|---|---|---|---|---|
| `query` | строка | да | | фраза или вопрос на естественном языке |
| `collection` | строка | нет¹ | | одна коллекция |
| `collections` | массив строк | нет¹ | | несколько коллекций, до 5 |
| `n_results` | целое ≥ 1 | нет | 5 | потолок 10 |
| `filter` | объект | нет | | условие по метаданным |
| `file_types` | массив строк | нет | | тип исходного файла |
| `contains` | строка | нет | | обязательная подстрока |
| `fields` | массив строк | нет | | какие поля метаданных вернуть |

¹ Нужен ровно один из двух: `collection` **или** `collections`. Ни одного —
«Не указана коллекция: передай „collection“ или список „collections“». Оба
сразу — «Переданы и „collection“, и „collections“ — оставь что-то одно».

Вектор запроса считает приложение моделью, привязанной к коллекции. При поиске
по нескольким коллекциям вектор считается **один раз**.

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"search","arguments":{
   "collections":["base_docs","corpus_recursive"],
   "query":"порядок приёмки работ",
   "n_results":5,
   "file_types":["word","pdf"],
   "filter":{"doc_type":{"$eq":"Документ"}}}}}
```

Ответ — `documents[]`, от ближайшего к дальнему. У каждого:

| поле | значение |
|---|---|
| `id` | идентификатор документа |
| `text` | текст, длинный — обрезан с пометкой |
| `metadata` | метаданные чанка, в том числе `file_id`, `source_file`, `file_ext` |
| `distance` | расстояние; меньше — ближе. Метрика указана в ответе |
| `collection` | из какой коллекции результат (при поиске по нескольким) |
| `note` | пометки: обрезка, контекст, урезание выдачи |

К результату может прилагаться раздел-родитель, помеченный как контекст, — он
не занимает место среди запрошенных результатов.

**Про счёт по выдаче.** Фрагмент — кусок файла, а не файл. Для расчётов берите
файл целиком через `get_file`. Одна строка таблицы — одна позиция; перечисление
внутри ячейки новых позиций не создаёт.

**Поиск отвечает на «что здесь самое подходящее».** На вопрос «покажи все
места, где это есть» он не отвечает ни при каком `n_results` — как это решается,
показано в

### 5.4. `get_documents` — документы целиком

Право: **чтение**.

| параметр | тип | обяз. | умолчание | описание |
|---|---|---|---|---|
| `collection` | строка | да | | имя коллекции |
| `ids` | массив строк | нет | | если задан, `filter` и `offset` не применяются |
| `filter` | объект | нет | | условие по метаданным |
| `file_types` | массив строк | нет | | тип исходного файла |
| `contains` | строка | нет | | обязательная подстрока |
| `limit` | целое ≥ 1 | нет | 5 | потолок тот же, что у поиска |
| `offset` | целое ≥ 0 | нет | 0 | для листания |
| `fields` | массив строк | нет | | какие поля метаданных вернуть |

Расстояний здесь нет, **порядок произвольный**. Векторы не возвращаются никогда.

```json
{"jsonrpc":"2.0","id":4,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs",
   "ids":["7b0d604937-0","7b0d604937-1"]}}}
```

Листание по фильтру:

```json
{"jsonrpc":"2.0","id":5,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs",
   "filter":{"file_ext":{"$eq":"pdf"}},
   "limit":10,"offset":20}}}
```

### 5.5. `get_file` — файл по порядку: оглавление, раздел, страница

Право: **чтение**.

| параметр | тип | обяз. | умолчание | описание |
|---|---|---|---|---|
| `collection` | строка | да | | имя коллекции |
| `file_id` | строка | нет² | | отпечаток файла из метаданных, 16 знаков |
| `file` | строка | нет² | | значение `source_file` — путь относительно папки источника |
| `as` | `chunks` \| `text` | нет | chunks | `text` — сплошной текст документа вместо списка чанков; `limit` и `fields` при нём не действуют, и ответ об этом говорит |
| `outline` | булево | нет | false | вернуть **устройство** файла, а не текст |
| `outline_depth` | целое ≥ 1 | нет | 1 | до какого уровня разворачивать карту; с `heading` считается **от него** |
| `heading` | строка | нет | | читать один раздел: значение `heading_path` |
| `limit` | целое ≥ 1 | нет | 5 | чанков за раз; при `outline` не действует |
| `offset` | целое ≥ 0 | нет | 0 | с какого чанка продолжать; с `heading` считается **внутри раздела** |
| `fields` | массив строк | нет | | какие поля метаданных вернуть |

² Нужен `file_id` **или** `file`. `file_id` надёжнее: путь легко испортить при
перепечатке.

**Порядок чанков гарантирует только этот инструмент.** У `get_documents` по
фильтру порядок произвольный.

#### Документ целиком: два способа, оба дешёвые

Задача «агент должен получить документ целиком» законна, и приложение обязано
дать способ, а не объяснять, почему не стоит.

**Способ первый — файл на диске.** Агент работает на той же машине. Каждый
ответ `get_file` несёт `sourcePath` — путь к исходному файлу, разобранный тем
же кодом, каким его открывает просмотрщик, и только если файл на месте.
Один шаг, ноль знаков в контексте, текст из первоисточника. Для документа,
пришедшего не из файла, поля нет.

**Способ второй — сплошной текст, и это умолчание.** Текст документа
вместо списка чанков: без идентификаторов, без метаданных, без зеркала в
`structuredContent`. Текст уезжает **один раз**.

Замер на ответах одного размера: чанками — 6 960 знаков документа, текстом —
20 880. Разница троекратная, и ответ при этом меньше — причём **честно**
меньше: метки, описание, общий блок метаданных и зеркало платят из того же
бюджета. Для ТЗ на 1281 чанк — разница между тремя с лишним сотнями вызовов и
восемью десятками; конкретное число для файла в руках называет карта, полями
`callsToReadWhole` и `charactersEstimate`.

**Потолок ответа — в знаках, и держится он у всех инструментов.** Считается
всё, что уезжает: строки для модели, зеркало в `structuredContent`, заголовок
ответа и пометки. Мерка одна — знаки, те же, в которых потолок объявлен ключу
; прежде зеркало считалось байтами UTF-8, и на кириллице русский ответ
урезался до трёх четвертей обещанного. Сторож гоняет семь вызовов при двух
потолках без допуска.

**Когда всё-таки чанки — общее не повторяется.** Метаданные, одинаковые
у всех чанков ответа, уезжают один раз полем `sharedMetadata`, а у чанков
остаётся то, что меняется. Замерено на живом ТЗ: 1 158 знаков метаданных на
чанк, из них 802 (69 %) байт в байт одинаковы у всех 1281 — имя файла, размер,
хеш содержимого, пометки извлечения, тип документа. Ответ на четыре чанка вёз
их четырежды, при том что файл назван в его же шапке. Блок платит из бюджета
ответа, как и всё, что уезжает вместе с текстом. Своя проекция агента
(`fields`) не подменяется: он назвал поля сам.

Умолчанием текст стал не сразу: сперва режим просто существовал, описанный в
скилле пятью строками и в схеме — с этим самым замером. За всё время его
выбрали **ноль раз из 183 вызовов** `get_file`. Совет как средство на этом
исчерпан. Чанки остались там, где их спрашивают явным `as: "chunks"`, и там,
где передан `fields`: проецировать поля в тексте нечего.

Куда уходило: текст ехал **дважды** — строкой модели и зеркалом в
`structuredContent`, — а метаданные, которых агент не просил, весили 1 223
знака на чанк против 1 180 знаков самого текста.

**Что именно едет.** Описание документа — **один раз**, только с первой
страницей: поле `document` в структурированном ответе и одна строка в тексте.
Там всё, что известно о файле: чанки, разделы, токены, страницы, байты, дата
правки, язык, пометки извлечения. Ни пути на диске, ни числа чанков в описании
нет: первое уезжает полем `sourcePath`, второе — полем `totalChunks`, и оба на
**каждой** странице. Два имени для одного значения заставляли бы клиента гадать,
одно ли это. Метаданные лежат у каждого
чанка, и на семидесяти страницах повторённое описание съело бы больше целого
ответа, ничего нового не сказав.

Дальше — только текст, и в нём **только метки последовательности**:
`[chunk N]` перед каждым чанком и `[chunk N · раздел]` там, где сменился
раздел. Метка отвечает на вопрос «где я и на что ссылаться»; имя раздела в
каждой строке было бы не меткой, а шумом. Конец назван концом:
`[end of document]` или `[end of section «…»]`.

Границы страницы называются **включительно** — «chunks 0–5 of 6», а не «0–6
из 6»: второе читается как семь чанков из шести и расходится с меткой
`[chunk 5]` в том же ответе.

Листается тем же `offset` в чанках; ответ называет следующий. Работает и
вместе с `heading` — тогда текстом приходит один раздел, `offset` считается
внутри него, а номера в метках остаются номерами документа, и ответ об этом
говорит. `limit` и `fields` здесь не действуют, и об этом ответ тоже скажет,
если их передали.

**Когда потолок ключа мал.** Обвязка ответа — описание файла, пометки, путь —
имеет свой размер, и у ключа с малым потолком она может занять его целиком.
Ответ без текста бесполезен, поэтому тексту отдаётся не меньше 2000 знаков —
и о превышении потолка сказано прямо, а не молча. Правило 3 приложения 5
в обратную сторону: вслух называется не только урезание, но и добавка.

**Швы.** Нарезка по умолчанию перекрывает чанки на 15 %, и склейка встык дала
бы документ с повтором на каждом шве. Срезается и шов **между страницами**:
для этого приложение подтягивает хвост предыдущего чанка. Без этого повторы
уходили внутри страницы и оставались на её границах — на семидесяти страницах
шестьдесят девять швов и около двенадцати тысяч повторённых знаков, при том
что пометка обещала «текст читается как документ». Перекрытие ищется по данным, а не по
настройке, и срезается; сколько срезано — сказано в ответе. Срез ограничен
половиной чанка: два **одинаковых** соседних чанка (шапка таблицы, бланк) дали
бы «перекрытие» во весь чанк, и срез удалил бы его целиком. Повтор агент
увидит и переживёт, пропажу — нет.

#### «Целиком» бывает недостижимо, и об этом говорится вслух

Файл на тысячу с лишним чанков не помещается ни в один ответ, ни в контекст
модели. Раньше инструмент этого не говорил: отдавал четыре чанка из 1281 и
выглядел успешным. Живой случай — ТЗ на 1281 чанк: агент прочитал двадцать три
и написал по ним «критический разбор требований», не заметив, что видел один
процент.

Теперь, когда чтение целиком требует больше десяти вызовов, ответ **начинается**
с приговора: сколько чанков в файле, сколько поместилось, во сколько вызовов
обойдётся — и что делать вместо этого. О токенах здесь не говорится: по пяти
прочитанным кускам вес целого не сосчитать — оценка разошлась с точной на треть
(342 027 против 500 625), — и вес отдаёт `outline`, где сложены все чанки.

В структурированном ответе — `fitsInOneAnswer` и `callsToFinish`. Первое
значит ровно то, что обещает именем: **весь файл в этом ответе**, а не «читать
недорого». Второе считает **оставшееся с текущего смещения**, а не весь файл
с нуля: иначе на последней странице из 1281 чанка ответ открывался бы словами
«читать так — двести пятьдесят семь вызовов» тому, кто дочитал 1276. Файл на
двадцать чанков, показанный по четыре с начала, отвечает
`fitsInOneAnswer: false` и `callsToFinish: 4`, хотя приговор вслух молчит:
порог решает, надо ли говорить, а не известна ли цена.

#### `outline` — устройство файла

Метаданные без текста: разделы по `heading_path`, границы в чанках, вес в
токенах. Оглавление документа на тысячу чанков само помещается в один ответ,
а чтение такого документа подряд не помещается никуда.

```json
{"jsonrpc":"2.0","id":6,"method":"tools/call",
 "params":{"name":"get_file","arguments":{
   "collection":"base_docs","file_id":"7b0d604937a1c2e4","outline":true}}}
```

Карта называет и `sourcePath` — её спрашивают первой, и именно из неё агент
должен узнать, что весь документ лежит рядом файлом. Переданные вместе с ней
`as`, `limit` и `fields` не действуют, и ответ об этом говорит.

Ответ: `sections[]` с полями `heading`, `firstChunk`, `lastChunk`,
`estimatedTokens`, плюс `totalSections`, `totalChunks`, `estimatedTokens`,
а также цена чтения целиком — `charactersEstimate` и `callsToReadWhole`
: по ним и выбирают маршрут.
`totalChunks` и `estimatedTokens` — всегда у **файла**, даже когда спрошен один
раздел: по этой паре решают, читается ли документ целиком. Размер и вес самого
раздела приходят отдельно, полями `chunksInSection` и `estimatedTokensInSection`
(в строке заголовка стоит именно вес раздела). Поля `documents` здесь нет и быть не может —
схема инструмента это описывает, см. «Схема ответа».

Глубина `outline_depth` отсчитывается **от спрошенного раздела**, а не от корня:
карта раздела «Требования» при умолчании показывает его части, а не сворачивается
в одну строку с ним самим. Это же и выход, когда карта целого файла не
поместилась, — пометка об урезании зовёт именно сюда.

Заголовков в файле может не быть вовсе (`heading_path` пишется не всякому
источнику). Тогда карта говорит об этом прямо, а не выдаёт один придуманный
раздел на весь документ за его устройство.

Разделы собираются **подряд идущими**, а не по имени: один заголовок
встречается в документе не раз, и «Общие положения» из начала слиплись бы с
одноимённым приложением.

#### `heading` — один раздел

Читает чанки, чей `heading_path` совпадает с названным **или начинается с
него**: «Общие положения» приносит и свои подразделы. Раздел — единица, о
которой можно рассуждать и которую можно назвать человеку; «чанки 200–203» —
не единица.

**Имя раздела — ключ, и оно приводится к набираемому виду.** В `heading_path`
живого ТЗ нашлись неразрывный пробел и перевод строки; на экране они неотличимы
от обычного пробела, и перепечатанное с карты имя не совпадало знак в знак.
Пробельное теперь сводится к одному виду и на карте, и в отборе: печатается
ровно то, что сработает. Промах по имени не отсылает за картой, из которой имя
и взято, — он называет ближайшие разделы (`nearestSections`).

Раздел, который не дочитать за десять вызовов, говорит это **первой строкой** —
тем же правилом, что и файл целиком; в структуре — `sectionFitsInOneAnswer` и
`callsToFinishSection`. Считается **оставшееся**, а не весь раздел: на последней
странице приговор молчит, а не советует бросить дочитанное. И совет в нём
исполним: к карте раздела отсылают только раздел с подразделами — у плоского
она вернула бы его же одной строкой. Живой случай: раздел на 47 чанков отдавал по четыре,
пометка лежала внизу среди прочих, и агент прочитал восемь чанков из сорока
семи — двенадцать разделов подряд, 48 чанков из 1281, и по ним разбор
требований.

Не поместился целиком — сказано прямо, с числом чанков в разделе и с тем,
каким `offset` продолжать: **смещение считается внутри раздела**. Без этого
раздел больше бюджета дочитать было нечем — ответ советовал взять остальное,
а параметра для этого не существовало, и повторный вызов отдавал те же чанки.

Чанки до первого заголовка оглавление показывает разделом
`(before the first heading)`, и спросить их можно тем же именем: раз карта
место называет, она обязана к нему вести.

Файла в коллекции нет — так и сказано, всеми тремя ветками одинаково: с
похожими путями, если файл с таким именем в коллекции есть, и с отдельной
пометкой про коллекции прежних сборок, где поля `file_id` ещё нет. «В файле
нет такого раздела» на промах по пути не отвечает никто.

#### Страницами, чанками

Чанки приходят по явному `as: "chunks"` — умолчание с отдаёт текст, —
и по переданному `fields`: проецировать поля в тексте нечего.

```json
{"jsonrpc":"2.0","id":6,"method":"tools/call",
 "params":{"name":"get_file","arguments":{
   "collection":"base_docs","file_id":"7b0d604937a1c2e4",
   "as":"chunks","limit":10}}}
```

Ответ: `documents[]`, `total`, `hasMore`, полный путь файла и `sharedMetadata`
— поля, одинаковые у всех чанков ответа, вынесенные из них один раз. Читать
страницами до `hasMore = false`, склеивая подряд, — годится, когда нужны
идентификаторы чанков; за текстом идут без `as`.

#### Поиск внутри одного файла

Отдельного параметра не нужно: `search` с фильтром по отпечатку ищет по смыслу
внутри файла.

```json
{"collection":"base_docs","query":"требования к резервному копированию",
 "filter":{"file_id":{"$eq":"7b0d604937a1c2e4"}},"fields":["heading_path"]}
```

Для документа на тысячу чанков это **основной** способ ответить на вопрос о
нём: прочитать его целиком нельзя, а найти нужные места — можно.

### 5.6. `collect_mentions` — все упоминания по файлам

Право: **чтение**.

| параметр | тип | обяз. | умолчание | описание |
|---|---|---|---|---|
| `collection` | строка | да | | имя коллекции |
| `contains` | строка | да | | слово или его основа без окончания |
| `filter` | объект | нет | | условие по метаданным |
| `file_types` | массив строк | нет | | тип исходного файла |
| `fields` | массив строк | нет | | какие поля метаданных вернуть |
| `per_file` | целое ≥ 1 | нет | 1 | образцов текста с каждого файла, не больше 3 |
| `limit` | целое ≥ 1 | нет | 5 | сколько **файлов** показать; потолок ключа |
| `offset` | целое ≥ 0 | нет | 0 | сколько файлов пропустить |

Отвечает на вопрос «во всех ли документах это есть» — тот самый, на который
поиск по смыслу не отвечает ни при каком `n_results`. Коллекция
обходится **один раз**, совпадения раскладываются по файлам, файлы идут от
частого к редкому.

```json
{"jsonrpc":"2.0","id":9,"method":"tools/call",
 "params":{"name":"collect_mentions","arguments":{
   "collection":"base_docs","contains":"резервн",
   "limit":10,"per_file":1,"fields":["source_file"]}}}
```

Ответ: `totalMatches`, `totalFiles`, `files[]` (путь, `fileId`, число
совпадений), `documents[]` — образцы, `hasMore`.

Живой замер: «резервн» — **752 совпадения в 20 файлах за 1.1 с**, ответ 12 194
знака. Поиск по смыслу на ту же тему приносил куски трёх файлов.

Ограничения:

- сравнение **буквальное** — синонимов инструмент не подбирает, для этого
  `search`;
- `per_file` больше трёх не отдаётся; просьбу о большем ответ называет вслух;
- перечню файлов отведена половина бюджета ответа: если путей слишком много,
  показано будет меньше файлов, и об этом сказано пометкой;
- за один вызов собирается не больше 20 000 совпадений; если их больше, об этом
  сказано в ответе;
- `limit` считает **файлы**, а не куски.

### 5.7. `list_files` — файлы коллекции

Право: **чтение**.

| параметр | тип | обяз. | умолчание | описание |
|---|---|---|---|---|
| `collection` | строка | да | | имя коллекции |
| `name` | строка | нет | | часть имени или пути файла, без учёта регистра и «ё» |
| `folder` | строка | нет | | начало пути от корня источника, целыми папками |
| `filter` | объект | нет | | условие по метаданным — как у `search` |
| `sort` | строка | нет | `path` | `path`, `chunks` — крупные первыми, `modified` — новые первыми |
| `limit` | целое ≥ 1 | нет | 50 | сколько **файлов** показать, не больше 500 |
| `offset` | целое ≥ 0 | нет | 0 | сколько файлов пропустить |

Отвечает на вопросы «какие документы есть в коллекции», «есть ли договор
такого-то года», «что лежит в папке», и даёт `file_id` для `get_file` без
поиска. Поиск по смыслу на них не отвечает: файл, ни разу не оказавшийся близко
к запросу, в выдачу не попадает вовсе.

```json
{"jsonrpc":"2.0","id":10,"method":"tools/call",
 "params":{"name":"list_files","arguments":{
   "collection":"base_docs","folder":"Договоры/2030","sort":"modified"}}}
```

Ответ: `files[]` — путь, `fileId`, `name`, число кусков `chunks` и, если
записаны, `expectedChunks`, `bytes`, `modified`, `format`, `pages`, `source`;
`totalFiles` — сколько файлов подошло, `totalChunks` — сколько кусков прочитано,
`withoutFile` — записей без исходного файла, `hasMore`.

Как устроено:

- список собирается обходом метаданных **всех** кусков коллекции (или тех, что
  подходят под `filter`) — первый вызов на большой коллекции занимает секунды,
  страницы после него берутся из памяти; запись через приложение и смена числа
  документов собирают список заново;
- у файла, записанного ранней сборкой, `file_id` нет — `get_file` примет его
  путь в `file`, и ответ об этом говорит;
- кусков меньше, чем записала синхронизация (`expectedChunks`), — запись файла
  оборвалась, строка помечена;
- записи без `source_file` (добавлены агентом, импортом, вручную) — не файлы:
  они только посчитаны в `withoutFile`;
- страница укладывается в бюджет знаков ключа; если не уложилась, показано
  меньше файлов, и об этом сказано пометкой;
- тяжёлый вызов у ключа один за раз — общий с `collect_mentions`.

### 5.8. `add_documents` — запись

Право: **запись**.

| параметр | тип | обяз. | описание |
|---|---|---|---|
| `collection` | строка | да | имя коллекции |
| `documents` | массив объектов | да | минимум один |
| `documents[].text` | строка | да | текст; он же индексируется |
| `documents[].id` | строка | нет | не задан — приложение придумает своё |
| `documents[].metadata` | объект | нет | плоский: строки, числа, булевы |

**Разбиение на части не выполняется**: что прислано одним документом, то и
станет одним документом с одним вектором. Длинный текст делите сами.

```json
{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"add_documents","arguments":{
   "collection":"notes",
   "documents":[
     {"text":"Резервные копии проверяются на восстановимость раз в квартал.",
      "metadata":{"doc_type":"заметка","year":2026}}]}}}
```

Особенности:

- текст длиннее контекста модели отвергается с указанием, какой именно документ
  не прошёл;
- заданный, но уже занятый идентификатор отвергается целиком — **перезаписи не
  будет**;
- вложенных объектов и списков в метаданных база не принимает;
- при наличии схемы метаданные проверяются по ней;
- каждому документу проставляется `origin = "mcp"`.

Ответ: `ids[]` — идентификаторы записанного.

---

### 5.9. `delete_documents` — удаление

Право: **удаление** (отдельное от записи).

| параметр | тип | обяз. | описание |
|---|---|---|---|
| `collection` | строка | да | имя коллекции |
| `ids` | массив строк | да | минимум один идентификатор |

Удаления по фильтру нет намеренно: одно неточное условие сносит половину
коллекции, а отменить это нечем. Нужна группа — найдите её через
`get_documents` с тем же фильтром, посмотрите, что нашлось, и передайте
идентификаторы сюда.

```json
{"jsonrpc":"2.0","id":8,"method":"tools/call",
 "params":{"name":"delete_documents","arguments":{
   "collection":"notes","ids":["note-1","note-2"]}}}
```

Идентификаторы, которых в коллекции нет, ошибкой не считаются — они
перечисляются в ответе отдельно. Ответ: `deleted[]`.

## 6. Как решать типовые задачи

Инструменты выбираются не по привычке, а по вопросу. Два вопроса выглядят
похоже, а решаются разными инструментами:

| вопрос | инструмент | почему |
|---|---|---|
| «что здесь самое подходящее» | `search` | ранжирует по близости, отдаёт лучшее |
| «покажи все места, где это есть» | `collect_mentions` | один обход, ответ по файлам |
| «какие документы есть», «дай file_id» | `list_files` | строка на файл, без поиска |
| «дай сами куски с этим словом» | `get_documents` + `contains` | те же совпадения списком |
| «собери все значения колонки» | `get_documents` + `filter` | условие по метаданным, без близости |
| «прочитай документ целиком» | `get_file` | единственный, кто держит порядок чанков |
| «их слишком много, ответ обрывается» | параметр `fields` | метаданные занимают бюджет наравне с текстом |

Ниже — два разбора: что именно вызывать, что настроить и чего ждать.

---

### 6.1. «Собери все формулировки по теме» — не поиском

**Задача.** В коллекции полсотни технических заданий. Нужны *все* места, где
описана приёмка работ, — чтобы сравнить формулировки между документами.

**Чего делать не надо: просить у поиска побольше результатов.** Замер
считал, во сколько файлов темы попал хоть один подходящий кусок:

| тема | файлов с темой | n=5 | n=20 | n=50 | n=100 |
|---|---|---|---|---|---|
| приёмка работ | 14 | 3 | 5 | 9 | 11 |
| резервное копирование | 13 | 3 | 3 | 3 | **3** |
| отказоустойчивость | 16 | 2 | 4 | 5 | 6 |
| гарантийные обязательства | 9 | 4 | 5 | 5 | 6 |

«Резервное копирование» стоит на трёх файлах из тринадцати **при любом числе
результатов**: близость возвращает соседние куски тех же документов, а
остальные десять файлов просто дальше по вектору. Поднятие `n_results` покрытия
не даёт — оно даёт длину.

**Что делать.**

**Шаг 1. Проверить, что слово вообще есть в текстах.** Не «звучит правильно», а
встречается: `contains` сравнивает подстроки буквально. Берётся основа без
окончания — «приемк» найдёт «приемка», «приемки», «приемке».

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs","contains":"приемк","limit":3}}}
```

Пустой ответ значит, что слова в корпусе нет, — и никакой поиск его не найдёт.
Так проверяется догадка, а не подтверждается: формулировка «экранная форма» на
живой базе дала ноль кусков, хотя выглядела очевидной.

**Шаг 2. Спросить охват — одним вызовом.**

```json
{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"collect_mentions","arguments":{
   "collection":"base_docs","contains":"приемк",
   "limit":10,"fields":["source_file"]}}}
```

В ответе — сколько всего совпадений, в скольких файлах, и сами файлы от частого
к редкому с образцом текста. Живой замер: «приемк» — **164 совпадения в 18
файлах за 1.35 с**, ответ 9 864 знака. Дальше файлы листаются `offset`-ом.

**Почему не `get_documents` с `contains` и листанием.** Так тоже можно, и
ничего не потеряется, но каждый вызов заново обходит коллекцию:
2136 совпадений страницами по 37 — 58 вызовов и **51 секунда** против
**1.35 с** одним обходом. И ответом будут две тысячи кусков вместо списка
файлов, то есть не тот ответ, который был нужен.

Нужны сами куски, а не охват, — тогда `get_documents`:

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs","contains":"приемк","limit":100,"offset":0}}}
```

Листать по `offset` из ответа: он учитывает, что список мог оборваться по
объёму, а не по числу документов.

**Шаг 3. Убрать из ответа лишние поля.** У текстового куска метаданных не
меньше, чем у строки таблицы: путь, заголовки, номер документа — 1246 знаков
против 1032 знаков собственного текста. Для сравнения формулировок из них нужен
один `source_file`:

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs","contains":"приемк",
   "fields":["source_file"],"limit":100}}}
```

Замер на живой коллекции: метаданных на кусок 1246 → **115**, кусков в одном
ответе (бюджет 24 000, текст до 800 знаков) **12 → 26**.

**Шаг 4. Настроить ключ под задачу** (экран «Клиенты»):

| поле | во что поставить | зачем |
|---|---|---|
| Результатов в MCP | 100 | иначе страница обрывается на десяти |
| Символов в документе | 800–1000 | нужна формулировка, а не документ целиком |
| Символов в ответе | оставить 24 000 | с `fields` и урезанным текстом бюджет перестаёт быть узким местом |

Уменьшать «Символов в документе» здесь выгоднее, чем поднимать общий бюджет:
задача — сравнить *разные* формулировки, а не прочитать каждую целиком.
Понадобится полный текст — он берётся отдельным вызовом по `id`.

---

### 6.2. «Собери все цены из таблиц» — фильтром по колонке

**Задача.** Шесть десятков таблиц, в каждой цена одного и того же товара. Нужны
все значения сразу, чтобы сравнить.

**Шаг 1. Узнать имена колонок.** Строки таблиц попадают в коллекцию так, что
каждая колонка становится полем метаданных. Имена показывает
`describe_collection` — он берёт выборку с пяти мест коллекции и отдельно
спрашивает строки таблиц, так что колонки видны, даже когда строк в коллекции
шестая часть.

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call",
 "params":{"name":"describe_collection","arguments":{"collection":"base_docs"}}}
```

Имя колонки писать точно так, как оно названо в ответе, и сравнивать с числом,
а не со строкой: `2026` и `"2026"` — разные условия.

**Шаг 2. Взять строки условием по колонке.** Не поиском: «все цены» — это не
вопрос о похожести.

```json
{"jsonrpc":"2.0","id":4,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs",
   "filter":{"стоимость_тыс_руб":{"$gt":0}},
   "limit":30,"offset":0}}}
```

Условие `$gt: 0` отсекает строки, где колонки нет вовсе. Живой замер: **100
строк из 26 файлов за 188 мс**.

**Шаг 3. Назвать нужные поля.** Строка таблицы тащит в ответ **все свои
колонки**, а бюджет ответа считает метаданные наравне с текстом. Поэтому к
запросу добавляется `fields`:

```json
{"jsonrpc":"2.0","id":5,"method":"tools/call",
 "params":{"name":"get_documents","arguments":{
   "collection":"base_docs",
   "filter":{"стоимость_тыс_руб":{"$gt":0}},
   "fields":["source_file","row_number","стоимость_тыс_руб"],
   "limit":100}}}
```

Замер на живой коллекции (1290 строк таблиц, `MCPProjectionLiveTests`):

| выборка | метаданных на строку | строк в ответе на 24 000 |
|---|---|---|
| сто самых широких строк | 1883 → **94** | 8 → **56** |
| сто строк вразброс | 419 → **87** | 49 → **100** |

То есть шестьдесят цен забираются **одним вызовом**, а без `fields` — восемью,
если таблицы широкие.

**Обрезка текста тут не помогает** — место занимают колонки, а не текст: у
строки таблицы метаданных 270 знаков в обычном случае и до 2848 в широком,
а собственного текста — 89. «Символов в документе» в этой задаче трогать
бессмысленно.

| поле | во что поставить | зачем |
|---|---|---|
| Результатов в MCP | 100 | сколько строк за вызов |
| Символов в ответе | оставить 24 000 | с `fields` бюджет перестаёт быть узким местом |

Поднимать общий бюджет стоит только тогда, когда нужны **все** колонки: это тот
же объём в контексте модели, только оплаченный целиком.

---

### 6.3. Листание: что гарантировано, а что нет

- **Порядок у `get_documents` произвольный.** Страница вторая не «продолжает»
  первую по смыслу — она просто следующая порция того же неупорядоченного
  списка.
- **Но ничего не теряется.** Замер: выборка по `contains` бралась
  сначала одним запросом, потом страницами, и списки сравнивались — 164 куска
  по 10, 2838 по 100, 2136 по 37. Повторов 0, потерь 0.
- **Один вызов стоит около секунды** независимо от размера страницы: цена
  в обходе коллекции выражением, а не в передаче данных. 2136 совпадений
  страницами по 37 — это 58 вызовов и 51 секунда; тот же охват через
  `collect_mentions` — один обход за 1.35 с.
- **Не листать во время синхронизации** коллекции: список меняется под руками,
  и вот тогда пропуски и повторы становятся возможны.
- **Порядок чанков держит только `get_file`** — он забирает все чанки файла и
  сортирует их по номеру, а не полагается на порядок выдачи.
- **Следующий `offset` брать из ответа**, а не считать самому: ответ называет
  его с учётом того, что список мог оборваться по бюджету раньше, чем по
  `limit`.

---

### 6.4. Почему ответ обрывается раньше, чем ожидалось

Потолков три, и первым срабатывает не тот, о котором думают.

1. **Результатов в MCP** — сколько документов вообще спрошено.
2. **Символов в документе** — сколько текста от каждого попадёт в ответ.
3. **Символов в ответе** — общий бюджет: тексты **и метаданные** всех
   результатов вместе.

Третий стоит ниже произведения первых двух намеренно и обычно срабатывает
первым. Метаданные считаются вместе с текстом — иначе бюджет ограничивал бы
ответ только на бумаге: у текстового куска их 1246 знаков против 1032 знаков
текста, у широкой строки таблицы — до 2848.

Отсюда правило: когда ответ обрывается, первым делом стоит смотреть не на
потолки, а на `fields` — половину бюджета обычно занимают поля, которых вопрос
не касался.

Обрыв не молчаливый: в ответе сказано «показано N из M». Первый результат
отдаётся всегда, даже если занимает весь бюджет.

Пометка называет и то, что уменьшить, — **именем параметра того инструмента,
который отвечал**: `n_results` у `search`, `limit` у остальных. Рендер ответа
один на пять инструментов, и одно имя на всех означало бы совет, который
четыре из них отвергнут как неизвестный параметр. И называет, чего именно
показано меньше: у `get_file` это куски, у `collect_mentions` — образцы
текста, а перечень файлов там приходит целым.

## 7. Ошибки

Различаются два вида, и это не формальность.

**Ошибка протокола** — JSON-RPC `error`: неизвестный метод, неразобранный JSON,
неверный тип параметра.

```json
{"jsonrpc":"2.0","id":3,"error":{"code":-32602,"message":"Параметр «contains» должен быть строкой."}}
```

**Отказ инструмента** — обычный результат с `isError: true`: нет прав, коллекция
вне списка доступа, документ не прошёл проверку. Модель обязана такое **увидеть
и осмыслить**, а не получить сбой транспорта.

```json
{"jsonrpc":"2.0","id":7,"result":{
  "content":[{"type":"text","text":"Ключу не разрешена запись в коллекцию «notes»."}],
  "isError":true}}
```

## 8. Порядок работы агента

1. `list_collections` — узнать, где искать.
2. `describe_collection` — узнать поля, прежде чем строить фильтр.
3. `search` — найти по смыслу.
4. `get_file` — дочитать документ целиком, если фрагмента мало.
5. `get_documents` — добрать по известным идентификаторам или полистать
   коллекцию.

Запись и удаление — отдельными правами и только там, где это заведомо нужно.

Этот порядок — для вопроса «что здесь про это сказано». Когда нужен полный
охват, шаг 3 меняется на другой инструмент: `collect_mentions` — если вопрос
про слово («во всех ли ТЗ описана приёмка»), `get_documents` с `filter` — если
про колонку таблицы («все цены»). Разбор обоих случаев —

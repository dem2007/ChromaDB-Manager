# База документов ChromaDB Manager

Восемь инструментов MCP поверх локальной ChromaDB: поиск по смыслу, полный обход
по слову, чтение документа по его устройству, запись и удаление. Этот скилл — о
том, **какой инструмент отвечает на какой вопрос** и как не принять образец за
всю картину. О самой библиотеке Chroma — скилл `chroma`; этот про приложение.

Ничто здесь не привязано к конкретному корпусу. Имена коллекций, пути файлов,
имена полей и основы слов показаны заполнителями — настоящие бери из ответов.

## Когда применять

- Любой вопрос о корпусе, который держит ChromaDB Manager: спецификации,
  договоры, сметы, таблицы, заметки.
- Счёт, сравнение, суммирование — всё, где важен **охват**, а не пример.
- Не применять для: другой ChromaDB без этого приложения, поиска в сети, файлов
  на диске, которые никогда не индексировались.

## Что нужно

- **ChromaDB Manager запущен.** Помощник `chromadb-mcp` — клиент приложения; без
  него любой вызов отвечает «приложение не запущено».
- Сервер объявлен в настройках твоего MCP-клиента, ключ — в переменной среды
  `CHROMADB_MCP_KEY`. Ключ выдаётся в приложении на экране «Клиенты» и несёт
  права: чтение, запись, удаление, список коллекций и потолки результатов.
- Клиент добавляет к именам инструментов приставку — обычно
  `mcp__chromadb_manager__`, двойное подчёркивание, дефисы заменены
  подчёркиваниями. Точное написание бери из своего же списка инструментов.

## Язык

Сервер отвечает **по-английски**: названия инструментов, заголовки, счётчики,
предупреждения. Документы — на том языке, на котором собран корпус, и на нём же
даются основы для `contains` и имена колонок таблиц: это буквальные подстроки
корпуса, и передавать их надо так, как там написано.

Не позволяй английской обвязке утянуть за собой твой ответ: **отвечай
пользователю на том языке, на котором он написал.** Текст документов цитируй
в оригинале.

## Краткая справка

| вопрос | инструмент |
|---|---|
| «что там сказано про это» | `search` |
| «во всех ли спецификациях», «покажи все места» | `collect_mentions` |
| «собери все значения колонки» | `get_documents` + `filter` |
| «прочитай документ целиком» | `get_file` — он и отдаёт текст, — либо его `sourcePath` |
| «ответь на вопрос о большом документе» | `get_file` с `outline`, затем `heading` |
| «найди что-то внутри одного документа» | `search` + `filter` по `file_id` |
| «дай фрагменты с этим словом» | `get_documents` + `contains` |
| «где вообще искать» | `list_collections` |
| «какие там поля» | `describe_collection` |
| запись, удаление | `add_documents`, `delete_documents` |

## Порядок работы

1. `list_collections` — до каких коллекций достаёт этот ключ **и каковы его
   потолки**. Ответ их называет; прочитай их.
   *Сделано, когда:* имя коллекции взято из ответа, а не выдумано.
2. `describe_collection` — **до** того, как писать фильтр, а не после. Имена
   колонок таблицы угадать нельзя, а неверное поле вернёт пустоту, не ошибку.
   `filter` сравнивает значения целиком (`$eq`, `$ne`, `$gt`, `$gte`, `$lt`,
   `$lte`, `$in`, `$nin`, `$and`, `$or`), поиска подстроки в нём нет вовсе:
   подстроку ищет параметр `contains` — по тексту документов.
   *Сделано, когда:* каждое поле фильтра встречается в том ответе.
3. Инструмент из таблицы выше.
4. Для арифметики — и для любого утверждения о документе целиком — прочитай
   документ: прочитай его целиком (или открой `sourcePath`), когда нужен весь, и
   `outline` с последующими разделами, когда нужны только числа.
   *Сделано, когда:* итог собран из целых разделов или целого документа, но
   никогда со страницы, и файл, который не удалось прочитать целиком, назван
   таковым.

## Выбирай `n_results` — не бери умолчание

Умолчание — 5. Потолок принадлежит ключу и назван в `list_collections`; он
обычно много выше пяти. Пяти хватает, чтобы посмотреть, и никогда не хватает,
чтобы посчитать.

- чтение, «что сказано про X» — от 5 до 10;
- сравнение формулировок между документами — от 20 до 30;
- «собери всё», «везде ли это», итог — потолок, и даже тогда проверь охват
  через `collect_mentions`.

Запрос выше потолка не отвергается: выдача урезается, и об этом сказано.

## Охват: `collect_mentions`, а не `n_results` побольше

**Смысловой поиск охвата не даёт.** Измерено на живой базе: по одной теме поиск
возвращал фрагменты трёх файлов из тринадцати **при любом** числе результатов —
близость раз за разом отдаёт соседние фрагменты тех же документов. Рост
`n_results` покупает длину, а не охват.

```json
{"collection": "<коллекция>", "contains": "<основа>",
 "limit": 10, "per_file": 1, "fields": ["source_file"]}
```

- слово давай **основой без окончания**: «приемк» находит «приемка»,
  «приемки», «приемке»;
- сравнение буквальное — синонимов нет, для них есть `search`;
- `limit` считает **файлы**, не фрагменты; листай по `offset` из ответа;
- **файлов может прийти меньше, чем просил.** У ответа есть предел объёма, и
  длинный перечень урезается: измерено — при `limit: 100` и 120 подошедших
  вернулось 47 и пометка об этом. Полное число при этом не теряется — заголовок
  по-прежнему называет его: «N matches in M files, K shown», — а остальное
  дочитывается по `offset`;
- **`per_file` по умолчанию 1, и обычно это верно.** Подъём умножает ответ —
  измерено, при `per_file: 3` тот же ответ вырос с 6799 знаков до 10 735, — а
  дело здесь в сравнении формулировок между документами, а не в чтении одного
  из них. Большой ответ твой клиент может сбросить в файл, а там агенты
  начинают разбирать текст, который надо было прочитать из ответа. Всё, что
  говорит один файл, бери через `get_file` или `get_documents` с `contains`;
- `per_file` больше трёх не возвращается, и ответ говорит, что просьбу урезали.

### Читай итоги, а не пересчитывай их

Первая строка ответа их уже несёт: `«<основа>»: N matches in M files, K shown`.
Бери эти числа.

**Не пиши свой разбор поверх текста ответа.** Измерено на живом прогоне: агент
написал, и его регулярка посчитала файлами строки идентификаторов и строку
предупреждения — вышло «17 файлов, три из них без совпадений» там, где на деле
20 файлов и совпадения во всех. Все числа, которые он вывел сам, оказались
неверными; верными остались только переписанные из ответа.

### «Во всех ли документах» требует знаменателя

`collect_mentions` даёт **числитель** — файлы, где слово встретилось. Сколько
файлов в коллекции всего, он не знает, да и на настоящий вопрос не ответил бы:
«во всех спецификациях» — это не «во всех файлах», и какие файлы считать
спецификациями, знаешь только ты.

Поэтому, прежде чем сказать «не во всех», добудь знаменатель и назови его:

- перечисли файлы: `collect_mentions` с подстрокой, которая есть в каждом
  документе (хватает одной частой буквы), и `per_file: 1` — в заголовке будет
  `N matches in M files`, и это `M` и есть число файлов коллекции;
- или сузь `filter` до документов, которые и есть спецификации, и посчитай их.

Ответ вида «20 файлов из 120 в коллекции» чего-то стоит. Просто «не во всех» —
догадка, даже когда она случайно верна.

## Чтение документа

Документ целиком — достижим. **Недостижимо читать его фрагментами**: это форма
`get_file` по умолчанию, полезного в ней около пятой части объёма ответа, и на
ТЗ в 1281 фрагмент это вышло бы вызовов триста. Спросишь напрямую — ответ
начнётся с приговора: сколько фрагментов в файле, сколько поместилось здесь,
во сколько вызовов обойдётся, — а в структуре будут `fitsInOneAnswer` и
`callsToFinish` — счёт оставшегося оттуда, где ты стоишь, поэтому на последней
странице приговор молчит. Приговор называет две формы ниже; бери одну из них.

### Целиком: `sourcePath`

Каждый ответ `get_file` называет, где документ лежит на диске этой машины.
Если файлы оттуда читать можешь — это весь документ в один шаг и даром: ни
вызовов, ни контекста. Поля нет, когда документ пришёл не из файла (записан
агентом, взят из веба) или файла больше нет.

### Целиком: текст, и это умолчание

Чтение файла отдаёт сплошной текст, а не список фрагментов: без
идентификаторов, без метаданных у каждого фрагмента, без зеркала в
`structuredContent`. Замер на ответах одного размера: **6 960 знаков документа
фрагментами против 20 880 текстом**. На живом ТЗ это восемьдесят вызовов вместо
трёхсот восьмидесяти — и карта называет это число для файла, который в руках.

```json
{"collection": "<коллекция>", "file_id": "<file_id>"}
```

Проси `"as": "chunks"`, когда нужны идентификаторы для `get_documents` или
метаданные каждого фрагмента; переданный `fields` выбирает фрагменты сам —
проецировать в тексте нечего.

Что приходит:

- **описание документа — один раз**, только с первой страницей: `document`
  в структурированном ответе и одна строка в тексте — фрагменты, разделы,
  токены, страницы, байты, дата правки, язык, пометки извлечения. Запомни
  его: дальше оно не повторяется. Ни пути на диске, ни числа фрагментов в нём
  нет — их несут поля `sourcePath` и `totalChunks` на каждой странице;
- **дальше только текст** с метками `[chunk N]` — и `[chunk N · раздел]` там,
  где раздел сменился, — чтобы ты всегда знал, где находишься и на что
  ссылаться. **Метки убирай перед цитированием;**
- `[end of document]` (или `[end of section «…»]`), когда дальше ничего нет;
- `hasMore` и `nextOffset`, пока есть. `offset` считается во фрагментах;
- перекрывающиеся фрагменты склеены без повторов — и на границах страниц
  тоже, так что склеенные страницы ничего не повторяют, — и пометка говорит,
  сколько знаков срезано на швах;
- смещение за концом так и сказано, а не отвечает `hasMore: false`, будто
  документ дочитан, — и путь на диске при этом назван;
- `limit` и `fields` здесь не действуют: страница набирается под бюджет
  ответа, а метаданных в тексте нет вовсе. Если ты их передал, ответ скажет.

Вместе с `heading` приходит текстом один раздел. Там `offset` считается
**внутри раздела**, а номера в метках `[chunk N]` остаются номерами документа —
ответ об этом говорит.

### Частями: сначала карта

Страница документа — это не документ. Судить о требованиях, противоречиях или
итогах по одной странице — самая дорогая ошибка, какую эта база позволяет.
Когда нужна часть, а не целое, бери карту (`outline`), а по ней раздел
(`heading`) — оба ниже.

### `outline` — карта

Метаданные без текста: разделы файла, границы каждого во фрагментах и
приблизительный вес в токенах. Карта документа на тысячу фрагментов помещается в
один ответ; сам документ не помещается никуда.

```json
{"collection": "<коллекция>", "file_id": "<file_id>", "outline": true}
```

- в ответе `sections[]` с полями `heading`, `firstChunk`, `lastChunk`,
  `estimatedTokens`, а также `totalSections`, `totalChunks` и `estimatedTokens`
  всего файла — честный вес целого, сложенный по всем фрагментам. `totalChunks`
  и `estimatedTokens` всегда у **файла**, даже когда спрошен один раздел;
  размер и вес самого раздела приходят отдельно, полями `chunksInSection`
  и `estimatedTokensInSection`;
- `outline_depth` по умолчанию **1** — верхний уровень, для того карта и нужна.
  У спецификации сотни подзаголовков, и перечислить их все — это стена, а не
  карта;
- чтобы заглянуть глубже, спроси карту **одного раздела**: `outline` вместе с
  `heading`. Глубина считается **от этого раздела**, поэтому умолчание уже
  показывает его части. Это же и выход, когда карта целого файла была урезана
  по объёму — пометка об этом так и говорит;
- карта называет и `sourcePath`: вызов, который велено делать первым, он же и
  говорит, что весь документ лежит на диске. `as`, `limit` и `fields` на карту
  не действуют, и ответ об этом скажет, если ты их передал;
- фрагменты до первого заголовка — тоже раздел, и спросить его можно тем именем,
  под которым его показывает карта: `(before the first heading)`;
- заголовков в файле может не быть вовсе — `heading_path` пишется не всякому
  источнику. Карта говорит об этом прямо, а не выдаёт один придуманный раздел
  за устройство документа: такой файл читают страницами или ищут внутри него.

### `heading` — один раздел

```json
{"collection": "<коллекция>", "file_id": "<file_id>",
 "heading": "<заголовок из карты>", "limit": 20}
```

- заголовок приносит **и свои подразделы**: спросив главу, получишь главу с
  частями. Фрагмент без собственного заголовка принадлежит разделу, внутри
  которого лежит, — таблица или продолжение абзаца из раздела не выпадут;
- раздел, не поместившийся в один ответ, **дочитывается**: `offset` считается
  **внутри раздела**, и ответ называет число, с которого продолжать, —
  `nextOffset` вместе с `hasMore`, а `chunksInSection` говорит, каков раздел
  целиком;
- **заголовок — это ключ, и сравнивается он по сведённому пробельному.**
  Неразрывный пробел или перевод строки внутри заголовка на экране не видны;
  карта печатает набираемую форму, отбор её принимает. Промах по имени называет
  ближайшие разделы, а не отсылает к карте, из которой имя и взято;
- раздел, который не дочитать за десять вызовов, говорит это **первой строкой**,
  а в структуре — `sectionFitsInOneAnswer` и `callsToFinishSection`; считается
  **оставшееся**, поэтому на последней странице приговор молчит. Это не
  формальность: прочитать 8 фрагментов из 47 и пойти дальше — так разбор и
  получается по 4 % документа;
- раздел — единица, о которой можно рассуждать и которую можно назвать
  человеку. «Фрагменты 200–203» — не единица;
- смещение за концом файла или раздела так и называется и не выдаёт себя за
  пропавший файл.

### Поиск внутри одного документа

Отдельного инструмента не нужно: `search` с фильтром по файлу ищет по смыслу
только внутри него.

```json
{"collection": "<коллекция>", "query": "<что ищешь>",
 "filter": {"file_id": {"$eq": "<file_id>"}}, "n_results": 20}
```

Это верный ход для вопроса «сказано ли в этом документе что-нибудь про X» о
документе, который целиком не прочитать: карта говорит, какие есть разделы, а
поиск с фильтром — где тема живёт по всем ним сразу.

### Говори, что именно прочитал

Если документ не поместился, это обязано быть в ответе: какие разделы прочитаны,
сколько фрагментов из скольких и что осталось неоткрытым. «Спецификация
структурно полна» после пятидесяти фрагментов из тысячи трёхсот — это не
осторожность в оценке, это неверное утверждение.

## Несколько коллекций одним вызовом

Вместо трёх вызовов `search` по трём коллекциям передай их списком в
`collections`: вектор запроса считается один раз, у каждого результата сказано,
откуда он, а объединённый список переранжируется целиком, так что кандидаты
соперничают между коллекциями. Передавать `collection` и `collections` вместе
нельзя.

## Таблицы

Каждая колонка таблицы — поле метаданных; условие ставится на колонку, а не
через поиск по смыслу.

```json
{"collection": "<коллекция>",
 "filter": {"<числовая колонка>": {"$gt": 0}},
 "fields": ["source_file", "row_number", "<числовая колонка>"],
 "limit": 100}
```

`fields` здесь обязателен по сути: строка таблицы тащит в ответ все свои
колонки — измерено 1883 символа метаданных на строку против 94 после проекции, и
в один ответ помещается пятьдесят шесть строк вместо восьми.

Числа сравнивай с числами: `2026` и `"2026"` — разные условия, и второе не
вернёт ничего.

## Подводные камни

- **Слова, которого нет.** `contains` сравнивает подстроки буквально. Пустой
  ответ означает, что слова в корпусе нет и никакой поиск его не найдёт.
  Проверяй догадку одним коротким вызовом: очевидная на вид формулировка может
  дать ноль фрагментов.
- **Страница — это не файл.** См. «Чтение документа» выше: целое — чтением
  (текст — это то, что `get_file` и отдаёт) или через `sourcePath`, часть —
  через карту и заголовок. Страница — никогда.
- **Ответ обрезан.** Бюджет ответа считает метаданные наравне с текстом.
  Смотри на `fields` прежде, чем смотреть на потолки.
- **`get_documents` возвращает произвольный порядок.** Страницы листаются по
  `offset` из ответа. Порядок фрагментов держит только `get_file`.
- **Никогда не считай по фрагментам.** Фрагмент — кусок файла. Одна строка
  таблицы — одна позиция; перечисление внутри ячейки позиций не добавляет.
- **Пометки в ответе — это данные.** Если сказано, что таблица пришла плоским
  текстом или книга размечена не целиком, никакой итог на таком ответе строить
  нельзя.
- **Строй `$or` явно.** Приложение добавляет свои условия рядом с корнем и твою
  логику не ломает, но `{"поле": "А"}` и `{"поле": "Б"}` двумя вызовами — не то
  же самое, что один `$or`.
- **Удаление — отдельное право.** Ключ, которому разрешена запись, не может
  удалять, пока право на удаление не выдано; отказ об этом говорит. Удаления по
  фильтру нет вовсе, только по явному списку идентификаторов.
- **Первый вызов после запуска приложения медленнее:** модель эмбеддингов и
  переранжировщик загружаются по требованию.

## Проверка

Пять вызовов на любой коллекции, до которой достаёт ключ, — особый корпус не
нужен:

1. `list_collections` — коллекции видны и потолки названы.
2. `collect_mentions` с основой, частой в этом корпусе, и `per_file: 1` — в
   заголовке `N matches in M files`.
3. `search` по той же теме — файлов много меньше, чем `M`.
4. `get_file` с `outline` на `file_id` из этих же ответов — разделы приходят с
   границами во фрагментах и весом в токенах.
5. `get_file` с `as: "text"` на тот же `file_id` — первая строка описывает
   документ, в тексте стоят метки `[chunk N]`, а `sourcePath` называет файл на
   диске, если документ пришёл из файла.

Разрыв между вторым и третьим — причина, по которой охват спрашивают у
`collect_mentions`. Четвёртый и пятый — два способа держать документ: по карте,
когда нужна часть, и целиком, когда нужно целое.

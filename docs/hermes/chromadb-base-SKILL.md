# База документов ChromaDB Manager

## Когда применять

Любой вопрос по корпусу документов, лежащему в ChromaDB Manager: техзадания,
контракты, сметы, таблицы. Инструменты приходят с префиксом
`mcp_chromadb-manager_…`; называть их вручную не нужно.

Приложение **должно быть запущено** — без него сокета нет и вызов вернёт отказ.

## Выбор инструмента — по вопросу, а не по привычке

| вопрос | инструмент |
|---|---|
| «что здесь про это сказано» | `search` |
| «покажи все места, где это есть», «во всех ли ТЗ это описано» | `collect_mentions` |
| «собери все значения колонки» (цены, сроки, объёмы) | `get_documents` + `filter` |
| «прочитай документ целиком» | `get_file` |
| «дай сами куски с этим словом» | `get_documents` + `contains` |

**Поиск по смыслу полного охвата не даёт.** Замер на живой базе: по теме
«резервное копирование» `search` приносил куски трёх файлов из тринадцати
**при любом** числе результатов — близость возвращает соседние куски одних и
тех же документов. Поднимать `n_results` бесполезно: это даёт длину, а не охват.

## Порядок работы

1. `list_collections` — где искать.
2. `describe_collection` — какие есть поля метаданных. **До** построения
   фильтра, а не после: имена колонок таблиц угадать нельзя.
3. Инструмент под вопрос — по таблице выше.

## Охват темы: `collect_mentions`

Один обход коллекции, совпадения разложены по файлам: у каждого число
совпадений и образец текста, файлы от частого к редкому.

```json
{"collection": "base_adaptive", "contains": "резервн",
 "limit": 10, "per_file": 1, "fields": ["source_file"]}
```

- слово задаётся **основой без окончания**: «приемк» найдёт «приемка»,
  «приемки», «приемке»;
- сравнение **буквальное**: синонимов инструмент не подбирает — это работа
  `search`;
- `limit` считает **файлы**, а не куски; дальше — `offset` из ответа;
- `per_file` больше трёх не отдаётся.

Живой замер: «резервн» — 752 совпадения в 20 файлах за 1.1 с.

## Значения из таблиц

Каждая колонка таблицы — поле метаданных. Условие ставится по колонке, а не
поиском по смыслу:

```json
{"collection": "base_adaptive",
 "filter": {"стоимость_тыс_руб": {"$gt": 0}},
 "fields": ["source_file", "row_number", "стоимость_тыс_руб"],
 "limit": 100}
```

**`fields` здесь обязателен по смыслу.** Строка таблицы приносит в ответ все
свои колонки: у широких строк это 1883 знака метаданных против 94 после отбора,
и в один ответ вместо восьми строк входит пятьдесят шесть.

Числа сравнивай с числами: `2026` и `"2026"` — разные условия, второе вернёт
пустоту.

## Подводные камни

- **Слово, которого нет.** `contains` сравнивает подстроки буквально. Если
  ответ пуст — слова в корпусе нет, и никакой поиск его не найдёт. Проверяй
  догадку коротким вызовом, а не считай её подтверждённой: «экранная форма»
  на живой базе дала ноль кусков, хотя выглядела очевидной.
- **Ответ обрывается.** Бюджет ответа считает метаданные наравне с текстом.
  Первым делом смотри не на потолки, а на `fields`: половину объёма обычно
  занимают поля, которых вопрос не касался.
- **Порядок у `get_documents` произвольный.** Страницы листаются `offset`-ом
  из ответа — он учитывает, что список мог оборваться по объёму. Порядок
  кусков держит только `get_file`.
- **Считать по фрагментам нельзя.** Фрагмент — кусок файла, а не файл; для
  расчётов бери файл целиком через `get_file`. Одна строка таблицы — одна
  позиция; перечисление внутри ячейки новых позиций не создаёт.
- **Пометки в ответе — это данные.** Если сказано, что таблица пришла плоским
  текстом или книга проиндексирована не целиком, итоги по такой выдаче
  считать нельзя.

## Проверка, что всё работает

Три вопроса с известными ответами на коллекции `base_adaptive`:

1. `list_collections` — коллекция видна.
2. `collect_mentions` со словом «резервн» — 752 совпадения в 20 файлах.
3. `search` по той же теме — три-четыре файла. Расхождение с пунктом 2 и есть
   причина, по которой охват спрашивают `collect_mentions`.
